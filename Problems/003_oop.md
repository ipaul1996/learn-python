# Problem: Bank Account

## Scenario

A small fintech prototype needs a bank account that tracks a customer's balance and records deposits and withdrawals.

## Requirements

Model a single account with:

- An account holder name (set at creation, should not change casually)
- A balance that starts at zero
- `deposit(amount)` — adds a positive amount to the balance; reject zero or negative amounts
- `withdraw(amount)` — subtracts a positive amount; reject if insufficient funds or invalid amount
- `get_balance()` — returns the current balance

Invalid operations should fail clearly (raise an error or return a failure indicator — pick one approach and use it consistently).

## Constraints

- Amounts are numbers (int or float)
- Balance must never go negative through a successful withdrawal
- External code should not be able to set `balance = -100` directly without going through your rules

## Expected Behavior

```text
account = Account("Priya")
account.deposit(500)
account.withdraw(200)
account.get_balance()   → 300

account.withdraw(400)   → fails (insufficient funds)
account.deposit(-10)    → fails (invalid amount)
```

## Deliverables

- The account type plus a short demo
- One sentence on how you prevented direct balance tampering

## Decisions You Must Make

- What is public vs what should only be changed through methods?
- Where does validation live — in one place or scattered?
- Is a plain class the right tool, or is something else a better fit for a simple data holder with rules?

## Questions to Think About

- If `balance` were a public attribute, what could outside code do that breaks the rules?
- Should `get_balance` exist, or should balance be readable another way?

# Problem: Shipment Status Updates

## Scenario

A shipping system logs status changes. Every update must:

1. Validate the new status
2. Write a log line
3. Save the shipment's latest status

Three teams contributed pieces:

- **Validator** — checks that status is one of `pending`, `shipped`, `delivered`
- **Logger** — prints `LOG: status → <value>`
- **Store** — keeps the latest status string on the shipment object

The final shipment type must combine all three behaviors. When `update_status("shipped")` is called, all three steps run in this order: **validate → log → save**.

## Requirements

- Implement the combined shipment type using the three concerns above
- Each parent layer should contribute one step; the combined type must not duplicate all three steps inline
- `update_status` on the final type must produce:

```text
LOG: status → shipped
```

…and the shipment's stored status becomes `"shipped"`.

- Invalid status (for example `"lost"`) must fail at validation **before** logging or saving

## Constraints

- Each concern should live in its own parent layer (three parents total)
- Do not copy the full `update_status` body three times
- Use the normal way to chain parent behavior in order (e.g. `super()`)

## Expected Behavior

```text
s = Shipment()
s.update_status("pending")    → logs and stores "pending"
s.update_status("shipped")    → logs and stores "shipped"
s.update_status("lost")         → fails; status stays "shipped"
```

## Deliverables

- The three parent pieces and the combined shipment type
- Demo including one invalid status attempt

## Decisions You Must Make

- In what order should the parents be listed on the combined type so validation runs before logging and logging before saving?
- How do you call the next layer's logic without hard-coding parent class names everywhere?
- What goes wrong if one parent calls another parent's method directly by name?

## Questions to Think About

- If two parents both define `update_status`, which runs first?
- Why might validation need to run before logging in this design?

# Problem: Release Version Ordering

- `v1 == v2` — same major and minor
- `v1 < v2` — lexicographic on `(major, minor)` pairs

## Requirements

- Define a contract that **cannot be instantiated** until a provider implements all required behavior
- Implement two providers:

```text
checkout(CardProvider(), 100)     → Paid via Card
```

# Problem: API Page Reader

A data sync tool reads remote records page by page. Each page is a list of record IDs. For testing, pages are provided upfront as a list of lists:

```text
[["a1", "a2"], ["b1"], []]
```

```text
for record_id in reader:

```

…and receive `a1`, `a2`, `b1` in order, then stop. Empty pages are skipped (no items yielded from them).

## Requirements

- Build a reader type that accepts the pages structure at construction

- Pages may be empty

- The reader must implement the standard iteration protocol so `for` loops work

```text
reader = PageReader(pages)

list(reader)   → ["a1", "a2", "b1"]
```

## Deliverables
